# speed-up-spool-restore

## Why

服务端重启后要过很久才能监听。实测（香港生产机，2026-11-16）：

| 指标 | 值 |
|---|---|
| idem 条目 | 28,493 个（`.dat` + `.meta` 各一份 = 56,986 个文件） |
| idem 数据量 | 2.2 GB |
| sidecar 总量 | 11.8 MB |
| 重启到端口可用 | 原本 **90s**（全量扫盘重建事件索引）；v0.3.9 去掉事件扫描后 **9.5s** |
| 单条目成本 | ≈ 0.33 ms（3~4 次 syscall + JSON 解析） |
| 进程常驻 fd | **28,503**（每个恢复条目一个） |

剩下的 9.5s 不是"等待"，是**重复计算**：启动时逐条 `ReadFile(.meta)` + `OpenFile(.dat)` +
`Stat`，把「写的时候就已经知道」的元信息重新推导一遍。并行化只是把等待摊到多核，
CPU 与 syscall 总量不变——所以本变更不做并行，而是**让启动不再需要这些计算**。

顺带修掉一个潜在断崖：`restoreIdem` 里 `OpenFile` 失败会 `continue` 静默跳过条目。
现在 `LimitNOFILE=262144` 撑得住 28k fd，但换一台默认 1024/8192 的机器（或条目涨到
26 万）就会有一批条目**看不见**——续传变成 409，且不会有任何报错。

## 事实基础（决定设计的关键不变量）

1. **文件名可从 key 推导**：`promote` 只做 `tmp/<key[:16]>.dat` → `idem/<key[:16]>.dat`
   的同名 rename。所以「按 key 找冷条目」= 直接打开两个已知路径，不需要索引。
2. **只有两件事需要 spool 在启动时可用**：
   - 续传按 key 找条目（`Acquire`）；
   - 字节预算收敛（`evictLocked`，纯后台策略，晚几秒无害）。
   两者都不要求"启动瞬间把 28k 条全装进内存"。
3. **spool 是缓存，不是账本**：miss 的代价是客户端重传一次完整请求（409 delta-miss），
   绝不会读到错字节。这条语义允许我们大胆惰性化——索引错了最多多一次重传。
4. `Manager.Stats()` 目前没有外部消费者（`cmd/server` 只用 `Acquire` / `Detach` / `Evict`）。

## What Changes

分四层，按收益排序；P1 单独就能消掉那 9.5s。

### P1 启动不扫描（核心）

- `New()` 只做 `MkdirAll`，**不** `ReadDir`、不 `Stat`、不 `OpenFile`。启动成本与 spool 规模解耦。
- `Acquire(key)` 在内存表未命中时做**冷查**：`idem/<key[:16]>.dat` + 同名 `.meta`
  存在且可解析 → 水合成 `Entry`（`state=Complete`、`inIdem=true`）并放进 LRU 前端。
  两条 syscall，只对"真的被续传的 key"付费。
- 冷查失败（无文件/半条 sidecar）→ 维持现有语义：新建 tmp 条目，由调用方回 409。

### P2 后台补水（不再阻塞可用性）

- 监听就绪**之后**起一个后台协程，分批（如 200 条/批、批间 10ms）扫描 `idem/`：
  填充热表、删除无 sidecar 的孤儿 `.dat`、统计字节并按 mtime 做预算收敛。
- 可取消（`Close`/`Stop`），速率限制避免和请求抢 IO；扫描完成前预算按"软上限"处理。

### P3 持久化索引（真正的"计算缓存"）

- `idem/index.ndjson` 追加写：`{"op":"put","k":<hex>,"f":<文件名>,"w":<明文长>,"z":<bool>,"n":<wire>,"st":<状态>,"t":<mtime>}`
  / `{"op":"del","f":...}`。写路径本来就要落 sidecar，追加一行是常数级增量。
- 启动/补水时**顺序读一个 3~4MB 文件**即可填满热表，替代 28k 次随机读 + 28k 次 open。
- 崩溃安全：索引只是 hint——末尾半行忽略；与目录列表对账；记录的 `wire` 与实际文件
  大小不符则丢弃该条（下次冷查会重新读 sidecar）。压实：追加条数 > 2×live 或文件 > 4MB
  时后台 `tmp+rename` 重写。

### P4 fd 纪律

- 冷条目按需打开，最多保留 64 个 LRU 句柄，空闲关闭。消除 28k 常驻 fd 与 ulimit 断崖。

## 验收标准

| 项 | 目标 |
|---|---|
| 50k 合成条目下 `New()` 耗时 | < 50 ms，且 `.dat` 读取字节数 = 0 |
| 冷查一条（`Acquire` 命中 idem） | ≤ 2 次文件打开 |
| 重启到端口可用（生产 28k 条） | < 1 s |
| 常驻 fd | < 200（与条目数无关） |
| 预算收敛 | 补水完成后总量 ≤ 预算（允许一个周期内的软超） |
| 续传正确性 | 冷查命中后按 event id 续传偏移与重启前一致 |
| 回归 | `go test -race ./...` 全绿；E2E 续传用例仍通过 |

## 风险与回滚

- 语义不变式不变：索引/水合错误只会造成 409（多一次重传），不会产出错字节。
- 新开关 `-spool-index=off`：关闭索引与后台补水，退回 v0.3.9 的 eager restore 行为。
- 上线顺序：v0.3.10 先在测试机造 5 万条目验证，再发生产；生产保留上一版二进制可回退。

## 非目标

- 不做并行恢复（治标，不减计算量）。
- 不改磁盘布局（不把多条数据打包进单文件）——那是下一个量级的问题（>10 万条目）。
