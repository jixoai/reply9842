## Why

README 第 3 条设计决策写着：

```
README.md:248
- **没有会话 ID**：服务端完全无状态，可水平扩展
```

这句与实现不符，且是实现方自己记录过的事实相矛盾：

1. **字典缓存是进程内的内存 LRU**（`internal/store/store.go`，`cmd/server/main.go:140`
   `store.New(c.cacheMB << 20)`）。它是**有状态**的：客户端把 `BaseHash` 发过来，服务端
   必须**同一台实例**上还留着那份 body 才能解码。多实例部署时请求落到别的实例即
   `DeltaMiss`，压缩收益归零（不会错，但退化成 zstd）。
2. **幂等区是磁盘 spool**（`internal/spool`，`-spool-dir` 单机目录）。断线续传必须回到
   同一台实例才能复用；跨实例续传必然 miss。
3. **`tmp/` 重启即清空**是刻意设计（进程内 goroutine 的 pump 随进程消失），这也意味着
   实例不可随意替换。

所以「完全无状态，可水平扩展」是**不成立的表述**。它会让运维按「无状态服务」的经验
做滚动重启与多副本扩容，进而遇到「压缩率突然归零」「续传全 miss」这类难以归因的现象。

这不是要求改成分布式——那会引入一致性协议，违背项目「越简单越有效」的立场。要求的是
**把真实语义说清楚**。

## What Changes

- 改写 README 第 3 条：明确「服务端**无会话/无协商状态**（这是与 SDCH 的本质区别），
  但**有缓存状态**（字典 LRU + 幂等 spool），因此单实例亲和」。
- `deployment` spec 增加「单实例亲和」的运维约束：滚动重启会导致短暂的压缩率归零与
  续传 miss，需要写进 DEPLOY.md 的运维注意事项。
- 若将来真要水平扩展，正确做法是**保持客户端粘性（sticky）到某实例**，或把 store
  下沉为共享 KV——但两条都是新设计，不在本 change 范围内（写明为「非目标」）。
- 可选：给服务端加一个 `X-Instance-ID`（或启动日志里的随机实例 id）便于运维确认
  「是不是换实例了」，以及 stats 里记录实例 id 便于事后归因。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `server`: 追加「单实例亲和」需求，修正「无状态」表述。
- `deployment`: 追加「滚动重启的影响必须写在运维文档里」需求。

## Impact

- 文档：`README.md`（第 3 条设计决策 + 已知限制）、`DEPLOY.md`（运维注意事项）、
  `site/index.html`（第 361 行有同样的「服务端完全无状态」表述）。
- 代码（可选）：启动日志与 stats 增加实例 id。
- 无功能变更；这是一次「把话说对」的修正，不涉及架构调整。
